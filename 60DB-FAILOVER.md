# 60db Failover Layer

Adds a reliability layer to the Inbound Voice Agent workflow: every speech
operation calls **ElevenLabs first** and **automatically falls back to 60db**
on any error, returning one **normalized, provider-agnostic** response.

> **Scope note.** This does *not* fail over the live ElevenLabs phone
> conversation — n8n is never in the real-time audio path, so it cannot take
> over a call mid-stream. It fails over the discrete speech *operations* (TTS,
> STT, voice listing) that tools or post-call processing invoke. True live
> failover would need a separate Twilio Media-Streams orchestrator.

## Endpoints (n8n webhooks)

| Capability | Webhook path | Primary (ElevenLabs) | Fallback (60db) | Input |
|---|---|---|---|---|
| TTS | `/60db-fo-tts` | `POST /v1/text-to-speech/{voice}` | `POST /tts-synthesize` | `?text=&elVoiceId=&voiceId60db=` |
| TTS stream | `/60db-fo-tts-stream` | `POST /v1/text-to-speech/{voice}/stream` | `POST /tts-stream` (NDJSON) | `?text=&elVoiceId=&voiceId60db=` |
| STT | `/60db-fo-stt` | `POST /v1/speech-to-text` (`scribe_v1`) | `POST /stt` (`language=auto`) | `?audioUrl=` |
| Voices | `/60db-fo-voices` | `GET /v1/voices` | `GET /myvoices` | — |

## How failover works

Each ElevenLabs HTTP node has `onError: continueErrorOutput`:
- **output 0 (success)** → Normalize → Respond
- **output 1 (error)** → 60db node → Normalize → Respond

The 60db node also has `continueErrorOutput`, so if *both* fail the response is
still well-formed with `success: false` and an `error` message.

## Normalized responses (the "consistent" contract)

```jsonc
// TTS / TTS stream
{ "success": true, "provider": "elevenlabs|60db", "audio_base64": "...", "format": "mp3", "sample_rate": 24000, "error": null }

// STT
{ "success": true, "provider": "elevenlabs|60db", "text": "...", "language": "en", "segments": [...], "error": null }

// Voices
{ "success": true, "provider": "elevenlabs|60db", "count": 2, "voices": [{ "voice_id": "...", "name": "...", "category": "...", "labels": {} }], "error": null }
```

Provider is detected by response shape: ElevenLabs TTS returns binary audio
(→ base64), 60db returns `audio_base64`; ElevenLabs STT has `language_code`,
60db STT has `request_id`; ElevenLabs voices use `voices[]`, 60db uses `data[]`.

## Setup

1. **Import** the updated `Inbound Voice Agent.json` into n8n.
2. Create two **HTTP Header Auth** credentials and select them on the new nodes:
   - **ElevenLabs API** — header `xi-api-key` = your ElevenLabs key
   - **60db API** — header `Authorization` = `Bearer <your 60db key>`
3. Pick default voices: set `elVoiceId` (ElevenLabs) and `voiceId60db`
   (a `voice_id` from `GET /myvoices`) per request, or hardcode them in the
   TTS nodes' `jsonBody`. The TTS nodes currently default ElevenLabs to
   `21m00Tcm4TlvDq8ikWAM` (Rachel) when `elVoiceId` is omitted.
4. Activate the workflow and hit the webhook URLs.

## Known limitation — WebSocket TTS

60db's true streaming socket (`wss://api.60db.ai/ws/tts`, with
`create_context`/`send_text`/`flush_context`) **cannot run in an n8n HTTP node**.
The `/60db-fo-tts-stream` endpoint uses 60db's HTTP NDJSON `/tts-stream` instead
(assembled into one base64 blob). For genuine low-latency WS streaming, run a
small external worker (Node + `ws`) or an n8n Code node with the `ws` module
available — see the WebSocket example in the 60db docs.

## Regenerating

The layer was generated by `build-60db-failover.js`. It is idempotent-unsafe
(re-running appends duplicates) — run it only against a clean export.
